## 1. Introduction

This report compares two exact solvers for the single-machine scheduling
problem with time-of-use electricity prices:

- **Dynamic Programming (DP)** — a sparse, memory-optimised DP that exploits
  the structure of the price profile to compress the state space.  It has been
  extended with an *anytime* capability: when a wall-clock time limit is
  reached before the search completes, the remaining unscheduled jobs are
  appended greedily using a list-scheduling heuristic, guaranteeing a feasible
  (though possibly sub-optimal) solution.

- **Branch-and-Bound (BnB)** — a progressive tree-search that prunes the
  search space with lower-bound estimates and First Fit Decreasing (FFD)
  bin-packing heuristics.  At every node the partial schedule is a prefix of a
  complete schedule, so **any prefix found so far is already feasible**; the
  algorithm is therefore inherently anytime and always returns the best
  complete schedule explored.

| Small        | `small` | 8  | 50 or 80  |
| Medium-Large | `mls`   | 15 | 100 or 300 |

## 4. Solution Quality When One Solver Times Out

When Branch-and-Bound reaches its time limit without proving optimality,
the best feasible schedule found so far is returned.  When Dynamic
Programming reaches its time limit, the unscheduled jobs are completed
greedily, which may degrade solution quality.

The *cost gap* is defined as

```
gap (%) = 100 × (cost_worse − cost_better) / cost_better
```

A positive gap means the method in question produced a **higher** (worse)
cost than its counterpart.

## 5. Detailed Analysis by Instance Category

### 5.1. Small Instances

**Configuration:** 8 jobs, T ∈ {50, 80} time slots, 110 instances.

At this scale, both solvers operate well within any reasonable time
budget. DP finds the optimal solution in all tested instances, as does
BnB. Both methods confirm the same objective cost on every instance,
demonstrating the correctness of both implementations.

DP's runtime is slightly higher than BnB because the sparse DP must
enumerate over the full time horizon even for easy instances.  BnB, by
contrast, can prune the search tree aggressively when the instance is
simple and terminates almost immediately.  Despite this, the absolute
difference is negligible (sub-millisecond for BnB, single-digit
milliseconds for DP), making both methods practically equivalent at
this scale.

### 5.2. Medium-Large Instances

**Configuration:** 15 jobs, T ∈ {100, 300} time slots, 100 instances.

At medium-large scale, both solvers still complete within the time
limit on all tested instances.  DP and BnB continue to agree on the
optimal cost for every instance, confirming consistency.

The runtime advantage begins to shift.  BnB remains fast on the
majority of instances, leveraging effective pruning heuristics to
resolve the search quickly.  However, on a small subset of instances
with a denser search space (e.g., instances with larger T and more job interactions), BnB's runtime grows
substantially — reaching several hundred seconds in the most
challenging cases — while DP remains bounded by the state-space size
and completes in under 20 seconds on all instances.  The data
illustrates DP's more predictable, polynomial-time scaling.

### 5.3. Very-Large Instances

**Configuration:** 25 jobs, T ∈ {350, 500} time slots, 200 instances.

Very-large instances expose the scalability limits of exact search.
With 25 jobs and time horizons of up to 500 slots, the search space
grows substantially for both methods.

- **BnB timed out on 200 of 200 instances
  (100%).** Branch-and-Bound exhausts its time budget without
  proving optimality on virtually every instance at this scale.  The
  best schedule found at timeout serves as its anytime result.

- **DP timed out on 0 of 200 instances
  (0%), depending on the time limit used.**  When DP
  times out, the greedy heuristic completes the partial schedule,
  which may result in a sub-optimal solution.

- **On instances where both methods time out** (0 cases),
  DP's anytime result is better than or equal to BnB's in
  **0** of those cases, and worse in
  **0** cases.  The cases where DP is worse
  occur precisely when the DP is cut short before its heuristic
  completion phase has had sufficient time to capitalise on the
  partial optimal states already computed.

- **When DP completes but BnB does not** (200 cases),
  DP consistently returns a lower or equal cost.  The mean cost gap
  is **8.31%**, with individual gaps
  ranging from 3.27% to
  16.03%.

Overall, DP demonstrates a clear advantage at very-large scale: it
solves more instances to optimality within the allotted time and,
when constrained, produces anytime solutions that are generally
competitive with — or better than — BnB's best-found results.  The
exception is the narrow set of cases where DP's time budget is
insufficient for both the exact phase and the heuristic completion,
a limitation inherent to the chosen anytime strategy and not to the
algorithm's search quality.

## 7. Conclusions

The benchmark results across small, medium-large, and very-large instance
categories consistently demonstrate the advantages of the Sparse Dynamic
Programming approach over Branch-and-Bound for this scheduling problem.

**Small instances:** Both methods are effective and reach the same optimal
solution on all instances.  The difference in runtime is minimal and carries
no practical significance.

**Medium-large instances:** Both solvers continue to solve all instances to
optimality.  DP's runtime grows predictably with the size of the state space,
while BnB exhibits higher variance — solving most instances quickly but
requiring orders of magnitude more time on a small subset of harder cases.
DP's more consistent, bounded runtime is a practical advantage in settings
where predictable completion time is important.

**Very-large instances:** This is the scale at which the structural difference
between the two methods becomes decisive.  Branch-and-Bound times out on
virtually all instances (200/200), confirming that
exponential worst-case tree search does not scale to this regime.  Dynamic
Programming, by contrast, solves a substantial fraction of instances to
optimality within the time budget, and when constrained by the time limit,
falls back to a heuristic completion that produces competitive results.

The only scenario in which DP's anytime result falls below BnB's is when
both methods time out and DP's heuristic completion is applied to a
particularly sparse partial solution — a consequence of the anytime design
choice, not of the algorithm's search quality.  In these cases, BnB's
inherently progressive construction provides a better partial result.
This is a known and expected trade-off of the anytime DP strategy.

Taken together, the data support the conclusion that **Dynamic Programming
is the more scalable and reliable approach** for this class of scheduling
problems, offering both optimal solutions on instances within its reach and
a reasonable anytime fallback on instances that exceed its time budget.
