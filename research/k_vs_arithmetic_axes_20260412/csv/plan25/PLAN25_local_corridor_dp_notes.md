# PLAN25: Local Corridor Exact DP — Notes

## Objective
Test whether a **local offset encoding** around the beam-prefix trajectory avoids the global mixed-radix int64 overflow that killed PLAN24B, while still providing a constrained exact search.

## Method
- `beam_corridor_local_dp` encodes state offsets relative to the beam prefix counts per block.
- Offset encoding: `id = Σ (offset[j] + delta) * (2*delta+1)^j`, which stays well within 32-bit integers for K=10, delta≤2.
- Candidate count vectors per block are generated by perturbing beam counts (single + pair moves), evaluated via `evaluate_profile_block_counts`, top 50 kept.
- Hard state cap: 5M states, time cap: 300s.

## Variants Run
1. `standard_step4` — baseline, no local corridor.
2. `local_corridor_delta1_300s` — delta=1, time limit 300s.
3. `local_corridor_delta2_300s` — delta=2, time limit 300s.

## Instances
- hardA_k10, n=1000, seed=0
- hardB_k10, n=1000, seed=2

## Key Findings
1. **No crashes, no memory issues**: Peak RSS 4–8 GB, well within limits. The local offset representation avoids the PLAN24B mixed-radix overflow.
2. **No incumbent improvement**: `best_ub = inf` on all local corridor rows. This does not yet prove the corridor lacks better completions, because the beam base path itself was not explicitly validated as surviving the local-corridor DP.
3. **State scaling is healthy**: delta=1 produces ~40–60k states; delta=2 produces ~7–14M states. `states_kept_max` stays well below the 5M cap and the theoretical per-layer max (3^10=59k for delta=1, 5^10=9.7M for delta=2).
4. **Time cost is modest**: 25–72 seconds per instance, but additive to the already long solver runtime.
5. **Exact sparse DP still skips**: `exact_diag_mode = sparse_skip_theoretical` on all rows. The global exact DP does not explore states; the local corridor is the only structured search happening in Step 4.

## Interpretation
- PLAN25 validates one narrow point: local offset encoding can run without the global int64 overflow seen in PLAN24B.
- PLAN25 does **not** yet validate the local-corridor algorithm as mechanically correct. Since the beam's own count vector is inserted as the base candidate for each block, an `infeasible_corridor` result is suspicious unless the base beam path is proven to be rejected for a specific, recorded reason.
- The current evidence is therefore **diagnostic/inconclusive**: either the corridor is too restrictive, or there is a block-alignment / candidate-evaluation / base-path-survival bug.

## Decision Recommendation
Given the cumulative evidence:
- PLAN24: theoretical guardrail → zero pruning.
- PLAN24B: forced global corridor → int64 overflow.
- PLAN25: local offset corridor → no overflow, but infeasible-corridor results require validation before any method claim.

The recommended decision is **C / diagnostic hold**:
- Keep the local-corridor code disabled by default.
- Do not use PLAN25 as evidence that the beam prefix is too close to optimal or that the corridor contains no better solution.
- Next required step is PLAN25B/PLAN26 validation: prove whether the base beam path survives, fix the `lb=ub` issue for corridor-limited UB improvements, and add block/count alignment diagnostics.
